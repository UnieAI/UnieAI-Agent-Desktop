# Agent Note: 桌面版中的 UnieAI 账号 API Provider

Status: implemented

[English](2026-08-22-unieai-cloud-providers-in-the-desktop.md) | 中文

## Problem

UnieAI Copilot 网页版有一个建立在 `user_providers` 之上的「API Provider 设置」页：账号自有的 OpenAI 兼容端点，每个带有全局唯一的四字符路由 Prefix、一份存储的凭证与一份模型目录。桌面版则有自己的「模型」页，建立在 `settings.yaml` 与 `ctx.credentials` 之上。两者是凭证生命周期不同的两个存储，而桌面版根本看不到账号的那份列表。

「显示相同的 Provider，并且能添加一个在两边都出现的 Provider」听起来像是同步需求，而同步两个各自独立的存储会引出三个没有默认答案的问题：Provider 在两边的身份是什么；同一行在两边都被修改时会怎样；以及 Provider 凭证是否要在服务端存储与一台笔记本之间移动。

## Decision

**不做同步，只有一份存储、一份镜像。** 网页版的 `user_providers` 仍是 API Provider 的唯一所有者。桌面版不保存副本：每份文档读取一次列表，创建之后再读一次，并且不把这些 Provider 的任何内容写进 `settings.yaml`。因此桌面版中显示的行与网页页面中显示的行是同一条记录——在桌面版添加的 Provider 之所以两边都出现，正是因为这一点，而不是因为复制了什么。

**身份就是产品的行 id，Prefix 作为给人看的句柄。** 本地不铸造任何标识。`user_providers.id` 是列表的键；`prefix` 是人们会复制与比对的值，因此用等宽字体呈现，也是拒绝信息所谈论的对象。

**冲突问题被消解，而不是被回答。** 桌面版不提供修改，也不提供删除。这不是界面上的省略——宿主路由只提供 `GET` 与 `POST`，而宿主所调用的产品路由也没有对应的 `PATCH` 或 `DELETE`。创建要么占到一个空闲 Prefix，要么被判为重复而拒绝，这是存储本就会给出的裁决；而同一行的并发修改则需要一个凭空发明的取舍规则，当其中一个字段是凭证时，无论「后写者胜」还是合并都不可接受。修改留在能看到整个账号的地方，本节用一行文字说明这一点。

**平台托管的 Provider 有双重不可及。** `user_providers.managedSource`（已绑定的 UnieAI Studio 目录，由产品自身的同步所有）会被投影为 `managed: true`；桌面版用产品自己的说明为它加上标注，并且不提供任何可改动的入口。真正的保障不是那个标注，而是根本不存在的写入。未带标记的行一律按托管处理，因此落后一次部署的宿主或产品也无法让托管的行看起来可编辑。

**凭证只朝一个方向移动。** 创建时把使用者刚输入的 API Key 送往产品——那才是要花用它的存储；这与在网页对话框中输入它是同一个动作，出于本人的明确意图，且表单本身写明了这些是谁的 Provider。返回方向不携带任何凭证。这比浏览器路由更严格：后者会在显示/隐藏字段中把 BYO 行自己的 key 回显给用户，而桌面投影对任何行都没有 `apiKey` 成员，因此也没有哪个字段会在日后被无意填上。把服务端持有的密钥复制到笔记本上会扩大其影响面，而这笔交易的另一侧什么也没有；至于托管行的 key——一份存活的 Studio 运行时凭证——本就不该由用户复制。

**这道缝就是登录闸门，正如 `/auth/account` 已经如此。** 认证 `/api/desktop/*` 的 API Key 存放在闸门位于宿主的会话表中，不得进入页面，因此由浏览器在 `/auth/providers` 询问宿主、宿主询问产品。创建所携带的 Provider 凭证走同一条路径。拒绝以产品自己的稳定标识符（`prefix_taken`、`byo_provider_limit_reached` 等）传递而非以文句传递，因为只有浏览器知道读者的语言；浏览器半边把每个标识符映射到一行文案，无法识别的标识符显示为通用的保存失败。

## Consequences

- 桌面版多了一个设置区块，排在「模型」之后。「模型」仍是桌面版自己的 Provider 界面，也是本机 Agent 实际运行所依赖的；本节则是云端账号的列表。两份列表互不包含对方的行，因此在一处删除不会看起来像在另一处也删除。
- `POST /api/desktop/providers` 强制执行的规则与浏览器创建路径完全相同——方案的 BYO 上限、`user_providers` 并无索引的三方 Prefix 唯一性，以及尽力而为的 `/v1/models` 抓取——做法是调用同一批 helper，而不是把规则复述一遍。此外它还限制提交字符串的长度，并拒绝非绝对 `http(s)` URL 的端点，因为桌面请求并非填写在本服务端渲染出来的表单里。
- 文案逐字取自产品的 `messages/{en,zh-tw,zh-cn,ja}.json`，每行旁标出来源键，四种发布语言齐备。两个产品呈现同一份列表，就不该互相改写措辞。
- 该列表中的 Provider 尚不能供桌面版自己的 Agent 使用。要让它们成为可选模型，就要把它们物化为 `llm-pi-ai` 路由，而这需要桌面版刻意不持有的凭证；在那之前，这里是账号管理界面，不是模型来源。
- 没有任何机制把 Provider 变更推送给桌面版，因此在别处添加的 Provider 会在下一次重试或重新加载时出现。

## Alternatives considered

- **把列表镜像进 `settings.yaml` 成为 `llm-pi-ai` 路由，并把每个 Provider 的 key 一并拉下来。** 因上文的凭证决定而否决：它把服务端持有的密钥——包括托管行那份存活的 Studio 运行时 key——挪到笔记本上，并且恰好重建了镜像所要避免的双存储对账。就「让这些 Provider 在本机可用」而言，物化仍然是正确的最终形态；不该随之携带的是那份密钥。
- **做一个照搬网页页面的完整编辑器，采用「后写者胜」。** 否决：落败的那次写入会悄悄丢弃一个可能是凭证或端点的字段，而用户永远不会知道自己的两次修改中哪一次留了下来。用版本校验代替时间戳，也只是把无声的丢失换成一个冲突对话框——而这个界面本就没有理由存在于桌面版。
- **把云端列表并入既有的「模型」区块。** 否决：两份列表的所有者不同、凭证存储不同、删除语义也不同。合并后的列表必须逐行说明这些区别分别适用于谁，而读者会合理地期待在一处删除会在另一处生效。
- **让浏览器带着桌面 key 直接调用 `/api/desktop/providers`。** 直接否决——那会把认证整个桌面界面的 key 放进页面。这正是 `/auth/account` 早已做过的决定。
- **在提交前于桌面版检查 Prefix 是否可用。** 否决：桌面版看不到账号里其他的 Prefix，而本地缓存的答案在别的客户端占用它的那一刻就已经过时。产品的拒绝是唯一正确的来源。
