# Agent Note：面向插件生态的上游名称转发包

Status: implemented

[English](2026-08-23-upstream-name-forwarders.md) | 中文

## 问题

本仓库中的每个包都已从 `@deepseek-ai/dsh-*` 改名为 `@unieai/uad-*`（[映射](../../../../docs/rescope.zh.md)）。社区插件生态并未随之改名，也不可能随之改名：已发布的插件在 peer 依赖中声明上游名称，并在 `dsh.client.inject` 下按名称列出它们，而这些 manifest 早已发布到 npm。

其后果并不是缺少某一项功能，而是所有第三方插件根本无法解析——一个约 1,900 条目的插件生态整体不可达，其中包括本仓库已排期工作的全部现成答案（通过 OAuth 接入用户自己的 MCP 服务器，以及计划预装的那些插件）。这些插件没有任何一点与本 fork 不兼容，不同的只是它们所请求的名称拼写。

## 决定

`healProfilesModuleFallback` 已经为每个已安装的包在扁平目录 `$DSH_HOME/profiles/node_modules` 中写入一个符号链接，Node 的逐级向上查找可从任意 profile 找到该目录。现在，在每个链接旁边，它还会以该包的上游名称写入一个**转发包**，其模块重新导出目标包。

上游名称由产品改名的逆运算得出，而不是来自第二份名单，因此两者不会发生偏离：`@unieai/uad-X` → `@deepseek-ai/dsh-X`、`@unieai/uad` → `@deepseek-ai/dsh`，其余 `@unieai/X` → `@deepseek-ai/X`（这一条覆盖了内置的框架包）。其他 scope 的包一律不动：给插件自己的依赖改名，等于发布一个其作者从未使用过的名称。

**转发包是真实目录，而不是第二个符号链接。** 这是承重的决定，而非风格取舍。在 Node 的默认解析下，符号链接会解析到其真实路径，因此指向同一个包的两个链接共享同一个模块实例，两种别名做法都可行。而在 `--preserve-symlinks` 下，两个链接解析为两个路径，该包会被实例化两次：两者之间的 `instanceof` 失败；对 `@unieai/cordis` 而言，这意味着两个 `Context` 类、以及完全不共享的服务。Electron 的 Node 采用 `--preserve-symlinks`，而桌面外壳正是在 Electron 中运行 harness——因此符号链接别名恰好会在本产品交付的场景下失效。转发包是一个独立模块，它重新导出的是一个只被加载一次的包，因此在两种模式下都到达同一个实例。

这一论断是被断言的，而不是被论证的：`legacy-alias.spec.ts` 构建一棵同时包含转发包与符号链接别名的目录树，在普通 Node 和 `--preserve-symlinks` 下各运行一次探针，并钉住「转发包在两种模式下都成立，符号链接只在其中一种下成立」。

只有当目标确实声明了 default 导出时，转发包才会具名转发它；这一信息从该子路径的 `.d.ts` 读取，而不是通过导入该模块获得——修复过程在每次启动时都会运行，而为检视命名空间去导入每个包，会在 Loader 尚未决定加载任何东西之前就执行插件的顶层代码。`export *` 从不带过 default，否则 service 包将转发不出它的类；而在目标没有 default 时凭空造一个，则会误报 function plugin 的形式，即 [postmortem 0001](../../../../docs/postmortem/0001-acp-default-export-drops-inject.zh.md)。

位于上游名称处、并非由本机制生成的转发包的目录，绝不会被覆盖，修复过程会改为明确报错：那个目录是别人安装的包，而静默替换它正是本机制要防止的那一种失败。

### 浏览器模块表是另一半

转发包回答的是 Node 的解析。插件的浏览器产物并不经过 Node：它是在插件自己的仓库中构建的，其打包器标记为 external 的东西，会变成由本产品的客户端模块表回答的 `require(...)`。`springbrand-lab/dsh-oauth-mcp-client` 把 `@deepseek-ai/cordis` 标记为 external，因此它的产物会向该表索取一个表中并不存在的键。

`makeRequire` 现在会在报错之前，按 `productNameFor` 重试一次未命中的 specifier——依次查 seed、已具现化的模块、已注册的 factory，顺序与第一次尝试相同。两个名称都不匹配的 specifier 仍会以其一贯的消息明确报错，因为该映射是结构性的：它会改写该 scope 下的任何名称，包括本仓库并未发布的名称，所以映射结果是「可以一试的候选」，绝不是该包存在的证明。

`dsh.client.inject` 无需任何改动。它是供 preflight 显示与 HMR 比对使用的信息性图元数据；真正约束代码到达的边由 `external` 承载。

这两个方向是同一条规则的精确逆运算，因此它们位于 `@unieai/uad-upstream-names`，而不在任何一个消费方内部。主机端问的是「这个包还响应什么名称」，浏览器端问的是「这个请求在这里意味着什么」。把同一条规则写两遍会让两者发生偏离，而这里的偏离会在运行时表现为无法解析的 import，而不是在构建时表现为类型错误。

## 考虑过的替代方案

**第二个符号链接。** 最直观的别名做法，也正是本方案所否决的：在默认解析下正确，在 Electron 的解析下失效，理由见上。

**在安装时对每个插件的源码做改名。** 本仓库已有一个可逆的 255 包改名脚本，因此这在机械层面是现成可用的。否决理由：它会改动第三方源码，于是每个插件都变成必须在每次升级时重新打补丁的本地 fork；而直接从 npm 或 git 安装的插件——也就是通常路径——根本不会经过它。

**在 profile manifest 中使用 pnpm alias 或 overrides。** profile 是一个真实的 pnpm 项目，`uad plugin` 又是 pnpm 的转发器，因此 `npm:@unieai/uad-X@*` 形式的条目确实能解析。否决理由：它需要在每个 profile 中为每个包各写一条，而该文件由用户编辑；并且它对那些经由 fallback（而非 profile 自己的 `node_modules`）到达插件的安装自有包毫无作用。

**向 npm 发布别名包。** 即以上游名称发布依赖我们的真实包。否决理由：这是在别人的 scope 下抢占名称。

## 后果

第三方插件无需改动即可解析，并已在真实目录树上验证：对实际安装执行修复会产生 206 个转发包；从某个 profile 目录出发，`@deepseek-ai/cordis` 在两种解析模式下都得到与 `@unieai/cordis` 相同的 `Context` 类对象。`@js2hou/dsh-mcp-manager` 可从 npm 安装进已修复的 profile，并解析到它所声明的内容。

该别名是单向的，且刻意如此：它让使用上游名称的消费方能够到达本产品的包，而不会让本产品在其他任何地方响应上游名称。

`./src/*` 这类通配符 `exports` 模式不在转发范围内：重新导出文件无法替代一个模式。它们是本仓库的源码层条目，由其自身的 tsconfig paths 与各项闸门读取，而不是由已安装的插件读取。

转发包并不能让一个本就不兼容的插件跑起来。它移除的是名称障碍；若插件调用的是本 fork 已经改动的 API，它仍会失败，只不过失败在那个 API 上，而不是失败在解析上。
