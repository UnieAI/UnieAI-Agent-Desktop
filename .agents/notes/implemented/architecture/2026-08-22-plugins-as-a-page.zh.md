# Agent Note：把「插件」做成一页，以及桌面版拿不到的 MCP 列表

Status: implemented

[English](2026-08-22-plugins-as-a-page.md) | 中文

## 问题

「插件」在这个产品里指两件不同的事，而侧边栏那一行指向了错的那一件。在 UnieAI Copilot 网页版里，「插件」是一个去处：账号安装的组合包与 MCP 服务器。在这个桌面版里，「插件」是设置面板里的 cordis 注册表——终端、Agent 循环、网页搜索——那个 `settings.section` 的自述是「本部署已安装的插件」。按下 外掛程式 打开的是部署内部信息，而标签承诺的是账号的插件。

那份注册表是真实的功能，不能删。它只需要不再独占那个词，也不再是一个产品级导航行单独打开的东西。

请求的另一半——像 UnieAI Studio 那样显示账号的 MCP 服务器——结果是一个关于「桌面版能诚实提供什么」的问题，而不是一件渲染工作。

## 决定

**「插件」是一个页面，不是设置分区。** 新的客户端包 `ui-plugins-page` 注册一个 `shell.overlay` 条目——运行时文档里为「浮在整个应用之上、属于你自己的表面」指定的座位——以及一个打开它的 `sidebar.nav.action` 行。页面拥有自己的外观、自己的开合状态，以及一个孔：`plugins.page.area`，一个 root 作用域的 list，所有者不提供任何东西，所以区块自己画标题和正文。

**cordis 界面换了座位，没有被重写。** `ui-settings-plugins` 把同一个 `PluginsSettingsSection` 组件、同样的标签页、同样的卡片、同一个 settings scope 注册到 `plugins.page.area` 而不是 `settings.section`。两个座位的 owner share 形状相同，所以组件只改了 props 引用的 slot 名。它的标题现在是「部署插件」，因为在页面自己的标题下再放一个「插件」，等于说这一页就是那份注册表。

**旧的导航行自己退场。** `ui-settings-general` 的「插件」行只在存在 `plugins` 设置分区时才绘制。移动分区恰好使该条件不成立，所以两行不可能同时出现，设置外壳一行也不用改——这一点很重要，因为同一时间别处正在改动那个包。

**Studio MCP 只列出，不连接，也不提供任何暗示它做得到的控件。** 缺的是三件各自独立的东西，而且都不在本仓库里：产品的 MCP 列表路由只认浏览器会话 cookie，桌面版的 API key 到不了；它的服务器摘要刻意只带来源地址而从不带端点，因为远程 MCP 的 URL 常在路径或查询串里夹带令牌；存储的请求头与 OAuth bearer 在服务端解密、从不投射给任何客户端。就算把列表给了桌面版，它仍然没有可以拨接的东西。安装按钮每按一次都会失败，所以一个都不画。

**404 是 `unsupported`，一个独立的状态。** 这个区块通过登录网关读 `GET /auth/mcp`，方式与 API Provider 分区读 `/auth/providers` 相同。本仓库没有主机提供该路由。404 被报告为「本版本没有 MCP 界面」，既不同于读取失败，也非常不同于账号没有任何服务器；把其中任意两者合并，就会在一个根本没能开口去问的页面上写下「你没有 MCP 服务器」。请求仍然会发出——每次打开页面一个 404——好让路由上线那天这个界面自动亮起来，浏览器端不必再改。

**行的类型没有 `url` 也没有 `headers` 成员。** 不是因为今天的主机不发它们，而是为了让将来的主机无法在没有人编辑这个类型的情况下，开始把凭证送到页面上。

## 后果

- 新的客户端包在四个必需位置注册（`tsconfig.client.json`、`tsconfig.base.json` 的 paths、web-app bundle patch 名册、web-app 清单）。它的名册行排在 `ui-settings-plugins` 之前，后者现在没有它就无处渲染。
- 页面打开时会盖住侧边栏，因为 `shell.overlay` 横跨整个框架，而布局所有者没有为导航栏旁边的表面声明座位。返回与 Esc 就是出口。要做成侧边栏旁边的页面，需要在 `ui-layout` 新增座位。
- 只要产品的 `messages/{en,zh-tw,zh-cn,ja}.json` 里存在对应文案，就逐字取用，并在每一行旁标注来源命名空间与键名，四个出货语言都完整。
- `webSearchDescription` 在一个已换品牌的应用里写着「The DeepSeek search provider」。厂商身份是真实的，保留；这一行现在把 DeepSeek 写成搜索 API 的供应方，而不是本产品自己。

## 考虑过的替代方案

- **让 cordis 界面继续注册为 `settings.section`，再为页面加第二个「插件」行。** 否决：两行同名，而且设置对话框仍然会用部署内部信息来回答一个产品级的问题。
- **像 `ui-trajectory` 注册视图那样，把页面渲染进对话栏。** 否决：`conversation.view` 是 session 作用域的，而「插件」与某个 session 无关——没有打开对话时页面将无法抵达。
- **从 overlay 的 DOM 祖先测量侧边栏宽度，让页面落在栏位旁边。** 否决：这会为一件本该由布局所有者声明的排版，把本包耦合到另一个包的元素顺序上。改为记录成上面的限制。
- **对着产品现有的 cookie 认证 MCP 路由，直接做安装或连接控件。** 否决：桌面版持有的是 API key 而不是会话 cookie，而且即使列表成功返回，也不带端点、不带凭证。提供一个不可能生效的东西，比诚实的空态更糟。
- **把完整 URL 与请求头投射给桌面版，让它直接连接。** 否决，理由与 API Provider 分区否决把 Provider 密钥拉下来相同：那会把服务端持有的机密搬到一台持有长期密钥的笔记本上。最终形态是产品托管、桌面版用自己密钥拨接的中继——一个带 `authorization` 请求头的 `streamable-http` 服务器，`dsh-mcp-client` 已经原样支持。
