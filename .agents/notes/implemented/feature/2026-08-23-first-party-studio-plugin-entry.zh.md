# Agent Note: 插件页面上的第一方 UnieAI Studio 条目

Status: implemented

[English](2026-08-23-first-party-studio-plugin-entry.md) | 中文

## Problem

插件页面不写死任何属于自己的插件。`DirectoryArea` 渲染 `/auth/plugins` 列出的内容，`StudioMcpArea` 渲染 `/auth/mcp` 列出的内容，两个组件都拒绝点名任何一个插件、分类或发布者：在客户端里写下一行，等于本包断言某个东西存在于一份属于产品的目录里，而只有那份目录才是这件事的权威。

这份拒绝让一件真实存在的东西没有被表达出来。UnieAI Studio 不是一行目录条目——它是本产品自己的账号绑定，正是它提供 Studio 的模型目录、账号自己的 runtime key，以及本页在下方已经画出来的那些 Studio MCP 工具。一个尚未绑定 Studio 的读者，无从在这一页得知这条绑定存在、它会带来什么、以及要去哪里完成它；而一个已经绑定的读者只看得到工具，却始终看不到它们从何而来。这两件事都不是对任何目录的断言，它们都是关于本产品的事实，在每一种部署里都成立。

这一页对「我绑定了吗」也一直没有可用的答案。`/auth/mcp` 早已带着这个答案——只有已绑定的账号，产品才会列出 id 为 `unieai-studio` 的服务器——但这一页此前只把那一行当成众多 MCP 服务器中的一台，没有从它的存在或缺席里得出任何结论。

## Decision

**这一页只承载一个存在被写死的条目，而且被写死的只有它的存在。** `plugins.page.area` 新增一个 id 为 `unieai-studio`、order 为 -20 的条目，由本包注册，并在 `directory` 去处上排在第一位——排在目录之上，因为它是本产品自己的整合，而它下面的那部分去处属于所有其他人。`studio-entry.ts` 写下了让这件事成为例外而非先例的规则：一个条目可以被写下来，前提是它是关于本产品的事实，而不是对某份目录的断言，并且它显示的一切仍然必须是读来的。

**它显示的一切都是读来的，而且读自本来就存在的那个 source。** 这个条目绑定的正是 `StudioMcpArea` 所绑定的同一个 `StudioMcpSource` 实例——同一个对象注入两处注册——因此条目与区块永远不可能对同一个账号各说各话。没有第二个读取器、第二条路由，也没有第二份缓存。`readStudioBinding` 是对 `StudioMcpState` 的纯投影，不是一次抓取。

**「已绑定」就是产品自己那一行的存在。** `/auth/mcp` 转发 `GET /api/desktop/mcp`，只有持有 Studio 绑定的账号才会被列出 `unieai-studio`。所以，一份已落定、含有那一行的清单是 `bound` 并带着那一行；一份已落定、不含它的清单是 `unbound`；而四种完全不带清单的读数——`loading`、`signed-out`、`unsupported`、`failed`——各自保留自己的名字，因为它们之中没有任何一种在说绑定是否存在。未登录的桌面端既不是已绑定也不是未绑定，并且会直说。id 采用逐字匹配，绝不按前缀：按前缀匹配会把一台恰好以同样字符开头的无关服务器认领过来。

**绑定动作只在一种读数下出现。** `unbound` 画出 綁定 / Bind，形式是 `<a target="_blank" rel="noopener noreferrer">`；`bound` 画出「已绑定」这个词，以及账号自己那台服务器所报告的工具名；`signed-out` 改为请对方先登录，因为绑定是一条账号链接，按下去只会落到登录页；`failed` 给出重试，而这四种里也只有它是重试能修好的。`bound` 但目录为空时，会说那台服务器没有报告工具，而不是画一条空条带；也不会为主机只给了一个名字的工具编造描述。

**绑定目标是 `https://agent.unieai.com/settings#profile`。** 这个路径是对着产品确认过的：`components/settings/studio-link-card.tsx` 对 Studio 跑完整的 OAuth device grant，它挂在产品设置页面的「个人资料」分页上，而 `settings-client.tsx` 会在加载时与 `hashchange` 时读取 `#<tab>`，因此这个 hash 能深链到那张卡片。不带语言区段：产品的 `next-intl` 路由跑的是 `localePrefix: 'always'`，不带前缀的路径会被重定向到访客自己协商出来的语言，在这里写死一个反而会覆盖他们在产品上选的语言。来源地址取的是 `unieai-web-gate` 的 `productUrl` 默认值，也正是 `packages/bundle/web-app/cordis.patch.yml` 为出厂桌面端配置的那一个——它对自架部署的代价见 [Consequences](#consequences)。

**标记是内联的。** 一张 754 字节的像素风 PNG，在 `studio-entry.ts` 里作为 `data:` URI，画在 40px 的方块里并带 `image-rendering: pixelated`。之所以内联：客户端 bundle 的纯度闸门禁止本包为运行期资源伸手到包外，而且桌面端会在离线状态下面对本地 harness 跑；之所以 pixelated：在方块尺寸下，任何默认的平滑滤镜都会把源图一像素宽的边缘糊成灰边。

## Why this one entry is hardcoded when the page refuses to hardcode others

这一页强制执行的规则并不是「绝不在客户端里写下任何一行」，而是**绝不断言别人目录里的内容**。这是两条不同的规则，而正是这个差别，让这个条目可以被接受，同时让「精选」标题、一行策划出来的市集条目、或一个发布者分组仍然不可接受：

- **一行目录条目是一个可能出错的断言。** `/auth/plugins` 决定什么东西存在、由谁发布、归在哪一类。在这里写下的一行，在目录变化之前是对的，之后就是错的，而且没有任何东西能察觉这种漂移。Studio 条目没有点名任何属于目录的东西。
- **这个条目的存在不可能是错的。** Studio 绑定是本产品的一项特性，在它的每一种部署里都存在，无论有没有账号用过它，也无论有没有目录路由会回答。写下它，并没有对桌面端所服务的那个产品之外的世界断言任何事。
- **关于它的一切会变的东西，仍然是读来的。** 是否绑定、工具名、工具数量、乃至究竟有没有账号，全都来自线上。被写死的部分只有一个名字、一句话、一张图标和一个 URL——而这四者里只有 URL 带着一项已知限制，它被记录在下面，而不是被藏起来。
- **未绑定状态正是它必须被写出来的全部理由。** 一个纯读取的条目，恰好会对它最该服务的那批读者消失：一个没有 Studio 绑定的账号拿到的清单里根本不会提到 Studio，所以一个只渲染线上内容的页面永远无法告诉他们这条绑定存在。那样的「拒绝写死」保护不了任何真实的目录，只会藏起一项真实的能力。

## Testing

`tests/studio-entry.client.spec.tsx` 对着渲染出的 DOM 钉住每一种读数：已绑定会点名所报告的工具且不提供绑定动作；未绑定提供该动作、指向 `https://agent.unieai.com/settings#profile`，并且是在桌面端旁边打开而不是把它导航走；未登录既不画已绑定也不画未绑定的说法，也没有动作；正在读取、不支持与失败各画自己的那一行，重试只出现在最后一种。一份只带其他服务器的清单读作未绑定，而 `unieai-studio-staging` 不满足那个 id。`readStudioBinding` 本身也被直接钉住：四种不带清单的读数，以及把产品送来的那一行交给已绑定读数。`tests/styles.client.spec.ts` 钉住 `image-rendering: pixelated` 与方块尺寸、「已绑定」一词上的成功色、绑定动作沿用的那颗安装药丸，以及这份样式表里不存在任何滚动容器。

## Alternatives considered

**去读产品来源地址，而不是写死它。** 因为在本包里够不着而否决：浏览器可以调用的路由里，没有任何一条会报告已配置的 `productUrl`。`/auth/mcp` 只会公布账号已经拥有的服务器的来源地址，而那按定义就不是绑定动作所面对的未绑定账号；`/auth/account`、`/auth/session` 与 `/auth/bootstrap` 都不带来源地址；而客户端插件不接受 `Config`，所以一个 cordis.yml 字段同样到不了浏览器。让网关公布 `productUrl` 可以闭合这一点，但那是 `unieai-web-gate` 的改动，不是本页的改动。

**画一句纯文字说明，而不是一条链接。** 否决，因为目的地是确认过的，不是猜的：绑定卡片、它所在的页面、以及它的深链机制，都是在产品源码里读到的。让读者自己去找设置页面的一句话，严格弱于一条真的能到那里的链接；而这条链接唯一可能出错的情形——`productUrl` 被指到别处——那句话同样帮不上忙。

**猜一个专用的绑定路径，比如 `/settings/studio` 或 `/link/studio`。** 直接否决。产品里没有这样的路由；一个编造出来的路径会在本次交付所面对的部署上 404，那比真正承载卡片的设置页面更糟。

**新增第二个直接读取绑定状态的 source。** 否决：`/auth/mcp` 已经回答了这个问题，`StudioMcpSource` 已经建模了未登录与不支持这两种读数，而第二个读取器会让请求翻倍，并制造出两份可能对同一个账号各说各话的状态。

**把这个条目放到配置去处，紧挨 Studio MCP 区块。** 否决，因为两者回答的问题不同。配置去处说的是「这套安装已经由什么构成」；这个条目说的是「这个账号还可以加什么」，并给出加它的手势，而那是目录去处的问题。

**从产品那里取图标。** 双重否决：客户端 bundle 的纯度闸门禁止这种对外引用，而且在一台离线面对本地 harness 的桌面端上，远程图片恰好会在网络本身出问题时裂成一个坏图。

**翻译产品名。** 否决，沿用该文件对 `Studio MCP` 的既有先例：这个名字在四份词典里都是字面量，因为被翻译过的产品名读起来像另一个产品。

## Consequences

这一页现在不必让读者打开配置去处就能回答「Studio 绑定了吗」，而一个未绑定的账号会被告知这条绑定带来什么、以及要去哪里完成它。这个条目不增加任何请求：它投影的是这一页本来就已经做过的一次读取。

绑定动作永远指向 `https://agent.unieai.com`，所以一个把 `productUrl` 指到自架 copilot-v2（`docs/unieai-development.zh.md`）的部署，会被这一条链接送到公开产品上。这一点连同它的闭合条件——网关把自己的 `productUrl` 公布给浏览器——一起记录在本包 README 的 Known Limitations 里。这个条目上其他每一项用户可见的事实都随部署正确，因为其他每一项都是读来的。

这一页现在有了一个被写出来的条目，而准许它的那条规则被写在下一个读者会遇到它的地方（`studio-entry.ts`、本包 README）。第二个想被写出来的条目必须通过同一道检验——关于本产品的事实，而不是对某份目录的断言——否则它不属于这里。
