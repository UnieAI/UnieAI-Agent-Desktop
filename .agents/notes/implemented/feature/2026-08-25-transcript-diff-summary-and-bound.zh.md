# Agent Note：訊息流的 diff 說出的變更量,與它能佔的高度

Status: implemented

[English](2026-08-25-transcript-diff-summary-and-bound.md) | 中文

## 問題

檔案編輯的 diff **本來就已經**渲染在訊息流的列裡——`file-mutation-row` 把 `diffCardModel(block)` 傳進 `ToolRow`,由共用的 `DiffBlock` 繪製,用的是詳情面板同一份模型。渲染器不需要任何抽取。

缺的是它周圍的三件事。收合的列只說了檔名、沒說變更量,於是「要不要展開」這個判斷只能靠展開來做。`DiffBlock` 自己的「顯示其餘」控制會把該列的行數上限解除、變成無界的主體,於是一次長編輯就能把其餘對話推出畫面。而 `str_replace_editor` 走的是泛用卡片,拿不到具名列才有的摘要。

## 決定

**收合的列標示 `+A −R`,而且和展開後 footer 用的是同一份算術。** 那些計數原本寫在一個 module-private 函式裡,要在卡片外面說出來就會變成第二套實作(行尾規則、去重路徑規則都得重寫)。`diffStats(diffs)` 改為匯出,兩個呼叫端共用,並用測試釘住——footer 和摘要不可能對不上。

**展開後的主體有高度上界,並在其中捲動。** 上限透過 `TerminalBlock` 已經在用的同一個可重綁自訂屬性掛在 `DiffBlock` 的主體上,所以什麼都不設的詳情面板仍保有全高的閱讀面。上限綁在**主體**而非卡片根部,因此複製控制與 footer 留在原位,只有 diff 的行在動。

**`str_replace_editor` 拿到摘要,但不套用具名列。** 它是多命令工具,其 `view` 與 `insert` 命令宣告 `card: 'generic'`;對那些命令而言,一個無條件的「Edit」標題與路徑連結是錯的。

## 考慮過的替代方案

**為訊息流另寫一套 diff 渲染器。** 在查證階段就否決:已經有一套而且是共用的,而要求「抽取」的那份規格是基於過期的前提寫的。

**用截斷 diff 模型的方式限制列高。** 否決:那樣計數描述的會變成「截斷」而不是「這次編輯」,而 footer 的「N 個檔案」也會和列上顯示的對不上。

## 後果

讀的人可以從收合的列決定要不要展開。長編輯留在自己的捲動容器裡。兩個說出變更量的地方是同一份實作,因此計數規則的改動不可能只落在其中一邊。
