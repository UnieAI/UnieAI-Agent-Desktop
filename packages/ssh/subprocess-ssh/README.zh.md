# @unieai/uad-subprocess-ssh

[English](README.md) | 中文

subprocess 接縫，放在一台透過 SSH 連到的機器上。掛載時取代 [`subprocess-local`](../../subprocess/subprocess-local/README.zh.md)，於是 harness 執行的每一個指令——Bash 工具的執行器、language server、搜尋——都移到那台機器上，而它們全都不知道這件事。

## 是改寫，不是重寫

這個 provider 繼承本機的那個，把每一份 spec 轉成同一個指令的 `ssh` 呼叫。改寫底下的一切都是本機 provider 的，已經寫好也測好：分離的行程樹、帶位移讀取器與溢出檔的 collect 模式、SIGTERM–緩衝–SIGKILL 的升級、釋放、以及行程結束時的收尾。在這裡，那套機制管的是代表遠端指令的那個 `ssh` 客戶端行程。

有兩件事在本機的意義必須重新指向：

- **工作目錄**是遠端機器上的。客戶端本身跑在 harness 使用者的家目錄，因為 spec 的 `cwd` 指的路徑通常不會同時存在於兩台機器上。
- **環境變數**屬於遠端指令，所以它們寫在命令列裡送過去，而不是給客戶端。客戶端自己需要的——`HOME`、`PATH`、agent 驗證用的 `SSH_AUTH_SOCK`——來自本機 provider 自己那份已清洗的父環境。

## 遠端行程的生命週期

**遠端指令活得比啟動它的連線久。** 對真實伺服器實測：殺掉本機客戶端之後，遠端指令仍在執行——有沒有配置終端機都一樣；而一個忽略 `SIGHUP` 的指令，兩種情況下都活著。

所以連線不是行程的把手，pid 檔才是。遠端 shell 先記下自己的 pid 再 `exec`——pid 仍然是指令自己的——而終止一次執行，是開第二條（重用連線，所以很便宜）連線去對那個 pid 的**行程群組**送訊號。群組正是它成為整棵樹終止的原因：在 sshd 底下，指令 shell 本身就是群組的 leader，所以一個訊號就能打到指令與它啟動的一切。沒有群組可打時，退回單一 pid。

終止會做兩邊，而且兩邊都需要：結束客戶端會釋放呼叫端的串流並讓結果落地，而遠端的訊號才是真正停下工作的那一半。

## 它拒絕什麼

- **終端機。** `spawnTerminal` 會丟出錯誤。繼承來的實作會配置一個**本機**終端機並在這裡執行 argv，於是使用者會拿到自己電腦上的 shell，而其他一切都在那台機器上——檔案系統與 subprocess 兩個 provider 就不再描述同一個執行世界，而那正是這個接縫的核心承諾。
- **相對的執行檔路徑**，與本機 provider 完全一致：它要解析的基準點並不存在，而跨過一個網路並不會生出一個。

## Model Experience

間接的，透過建立在 `ctx.subprocess` 之上的工具——首先是 Bash 執行器——由它們擁有所有面向模型的契約；此套件自己不註冊任何 tool、prompt 或 schema，只改變它們的工作發生在哪一台機器上。

#### KV Cache effect

無。這裡不產生任何 prompt 片段、工具定義或 context 條目。

## 已知限制與未完成項目

- **還沒有終端機。** `spawnTerminal` 直接拒絕，所以 `terminal-bash` 與使用者操作的終端機還不能跑在遠端機器上。缺的是遠端前景行程的檢視：本機 PTY 的前景行程永遠是 `ssh`，提示符與閒置偵測會把它誤讀成那個 shell。
- **遠端必須是 POSIX 類的登入 shell**，這一點記在[機器名冊](../ssh/README.zh.md)。
- **一次掛載一台機器。** alias 是設定，所以行程內的每一個 session 都跑在同一台機器上；要按 workspace 選擇，需要一個 harness 目前還沒有的路由器。
- **`exitCode` 255 是有歧義的。** 它既是 OpenSSH 自己的失敗碼，也是被終止的執行會回報的值，所以呼叫端無法只憑狀態碼區分「連線失敗」與「遠端指令被殺掉」。
