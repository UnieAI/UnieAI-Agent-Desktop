# @unieai/uad-client-unieai-bootstrap

[English](README.md) | 中文

UnieAI 桌面端的启动初始化。它在应用挂载之前发出一次请求——`GET /auth/bootstrap`——并把答复作为 `unieaiBootstrap` 服务发布出来：这台桌面端是否已登录，以及 host 已经代该账号取回了什么。

它之所以存在，是因为「这台桌面端是否已登录、它手上有什么」这个问题过去由每个需要它的界面各自回答。账户区块读 `/auth/account`，API Provider 区块读 `/auth/providers`，插件页读 `/auth/mcp`，各自在请求飞行途中发明自己的空状态。于是界面打开时各区块处在互不相同的状态里，而一台未登录的桌面端要把这件事重新发现好几遍。

## 形态：host 预取，浏览器只读一次

预取发生在 host 上，位于 `@unieai/uad-unieai-web-gate`，而不在本包。两个事实决定了这一点：

- **会话与桌面 API key 本来就在 host 手上。** 这些读取每一次都是由绝不可到达页面的凭据认证的产品调用，所以浏览器要四样东西，等于 host 照样要发四次以上的产品调用——而且每一次前面还多一次同源往返。
- **host 可以在浏览器存在之前就开始。** 设备码授权落地的那一刻预取就开始了，而那时浏览器还在从登录页跳往应用的路上。等本包开口时，答案通常已经在内存里。

因此浏览器只发一次请求，拿回一个 body。其中每一部分都**逐字等同于该部分自己的路由会给出的答复**——`parts.account` 就是一份 `/auth/account` 的 body，`parts.providers` 就是一份 `/auth/providers` 的 body，依此类推。本包不解析其中任何一份：每个消费方本就拥有自己那条路由的读取器，而在这里再抄一份这四种线格式，只会与原件产生分歧。

## 网络不好时会发生什么

桌面端的第一帧等待这次读取，因此这次读取必须结束。三个数值为它设界，而每一个的结局都是应用照常打开：

| 界限 | 数值 | 作用 |
|---|---|---|
| host 预取截止 | 2 秒 | host 用已到齐的部分作答，并点名仍在取的那些。 |
| 浏览器读取超时 | 3 秒 | 超过即放弃本次读取，快照为 `unavailable`。 |
| 追补延迟 | 1.5 秒 | `partial` 的答复在此之后于后台再问一次。 |

`unavailable` 不是给用户看的失败，而是给每个界面的指令：去读你自己的那条路由——那正是它们在本包出现之前一直做的事。于是产品不可达的桌面端打开的仍是原来那些界面，本地 agent 照常工作，没有任何东西在等云端。

未登录路径只花一次本地往返，且完全不等待：host 面对没有会话的浏览器不会去调用产品，因为既没有什么可取，也没有什么要拒绝。

## 它在启动序列中的位置，以及在那里阻塞为何是安全的

`packages/client/web/src/boot.ts` 先激活每个客户端入口，然后才挂载 React。本插件的 `apply` 是 `async` 的，因此在启动读取尘埃落定之前它的 fiber 一直处于加载中，而挂载所等待的 loader 静默期把它算在内。这正是这项功能本身：界面打开时已经知道自己有哪个账号。

有两个细节让这件事是稳的而不是脆的：

- **等待由本包设界，而不由网络设界。** 最坏情况就是浏览器读取超时，此后快照为 `unavailable`，一切照常继续。
- **`apply` 不能写成普通的 `function` 声明。** Cordis 对带 prototype 的插件体用 `new` 调用并丢弃其返回值；只有没有 prototype 的插件体——`async function` 或箭头函数——才被平常调用并让 fiber 等待它的 promise。若写成另一种，本插件会立即激活、挂载与读取赛跑，而所有测试依然是绿的。

## 消费方要 inject 它

启动答复的消费方要在自己的 `inject` 里写上 `unieaiBootstrap`。这不是关于可选服务的写法偏好：本包读取期间它的 fiber 并未 active，而 Cordis 不会交出 fiber 尚未 active 的服务。用 `ctx.get` 去找它的界面，在自己的 apply 时刻只会找到空，退回去读自己的路由，让取好的答复白白闲置。inject 同时保证消费方体内读到的快照就是已落定的那一份。

其代价是：保留消费方行却删掉本行的组合，会让那个消费方的 fiber 停在 pending——而这一点启动页会指名报出，不会无声无息。

`@unieai/uad-client-unieai-account-gateway` 是第一个消费方，也是其余消费方的样板：它的首个账号取自 `parts.account`，而其后它执行的每一次刷新——保存资料、发出邀请、重试——依旧直接读 `/auth/account`。启动答复描述的是文档的起点，它不是产品的缓存。

## Model Experience

无：本包为浏览器界面读取一次启动答复；此处没有任何东西会到达模型请求。

#### KV Cache effect

无；本包既不组装也不发送供应商请求。

## Known Limitations and Deferred Work

- **今天只有 account 部分有消费方**——答复里同样带着 `providers`、`models` 与 `mcp`，由 host 取好并缓存，但 `ui-unieai-providers` 与 `ui-plugins-page` 首次渲染时仍读自己的路由。那两个包由别处拥有；把它们接到本服务上是它们的改动而非这里的改动，在此之前它们的首读代价一如既往。
- **追补读取只做一次**——`partial` 的答复恰好换得再试一次。之后仍未到齐的部分交回给该界面自己的重试手势，因为不停追问的热启动就成了轮询，而这里没有谁知道产品打算花多久。
- **会话过期时快照不会被重读**——登录门的会话按闲置过期、在请求发生时才判定，因此开着超过闲置时限的桌面端，手上那份启动答复描述的是一个已不存在的会话。每个界面会在自己的下一次请求里发现这件事——那次请求答以 `signed-out`；在有人要求刷新之前，本包不会发布任何新东西。
- **它没有自己的可见加载态**——启动页既有的转圈已经覆盖了这段等待，本包不往上加任何东西。一次用满三秒的读取，看起来与正在加载插件的启动完全一样，因为它同时也确实在做那件事。
- **`refresh()` 是为完整性而在**——启动路径调用它一次，此外无人调用。想知道当前状态的消费方去读自己的路由，那才是说出「现在是什么」的东西。
