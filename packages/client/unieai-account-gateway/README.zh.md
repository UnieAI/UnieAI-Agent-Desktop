# @deepseek-ai/dsh-client-unieai-account-gateway

[English](README.md) | 中文

账号能力缝的 Provider 角色。`ui-unieai-account` 定义 `UnieAiAccountGateway` 并据此绘制账户设置区块；本包提供该服务的一个实现，数据取自登录门的 `/auth/account` 路由，写入则经由它的 `/auth/profile` 路由。省略本行的构建仍保留该区块，区块则报告尚未接上账号服务。

## 数字从哪来，为什么要经过 host

用于访问 UnieAI 产品 `/api/desktop/*` 接口的凭据存放在 host 上登录门的会话表中，而浏览器的会话 cookie 是 `HttpOnly` 的。本包读不到其中任何一个。它只发出一次同源的 `GET /auth/account`；由 host 解析会话、以该 API key 访问产品，并写回一份不含任何凭据的账号描述。写入走同一条路径、同一个方向：`saveProfile()` 提交 `/auth/profile`，持有 key 的始终是 host。

**第一次读取根本不在这里发生。** `@deepseek-ai/dsh-client-unieai-bootstrap` 发布桌面端的启动答复——那是 host 在应用挂载之前取好的一份 `/auth/bootstrap` body——本包的首个账号取自该答复的 `account` 部分，而那一部分逐字等同于 `/auth/account` 会说的内容。只有在根本拿不到启动答复时（构建里没有登录门，或 host 未能及时作答），或 account 不在已取到的部分之列时，本包才自己去读那条路由。无论哪种情况，下面描述的都是此后发生的事。

每个文档读取一次，另加每次写入之后一次。两个登录手势都以新文档收尾——`signIn()` 跳转到登录门在服务端渲染的设备码页面 `/auth/login`，`signOut()` 提交 `/auth/logout` 后重新加载——因此账号恰好在可能变化时被重新读取。登录无法在单页应用内完成：该页面在任何客户端产物存在之前就已由登录门渲染；这也正是本网关不发布「已登出与已登录之间」任何状态的原因。

## 它发布什么，以及拒绝发布什么

账号契约规定区块只渲染供应方回报的内容，因此映射是单向的：此处写入的每个字段都来自产品回报的字段。

| 产品用量键 | 限额 id |
|---|---|
| `agentTurns` | `agent-turns` |
| `agentTokens` | `agent-tokens` |
| `chatTokens` | `chat-tokens` |
| `mcpCalls` | `mcp-calls` |
| `toolCalls` | `tool-calls` |
| `agentSessions` | `agent-sessions` |
| `vlmPages` | `vlm-pages` |

产品未回报的用量项不会以零值出现，而是根本不出现在列表中；产品标记为不限量的额度保持 `limit: null`，不会退化成一条满格的进度条。`resetsAt` 由回报的 ISO 时刻按读者本地时区格式化为 `YYYY-MM-DD HH:mm`，未回报时刻则完全不出现重置行。`windowHours` 以数字传递，因为它所在的句子——「每 5 小时重置 · 下次 …」——是区块自己的文案，而不是只有产品能写的额度名称；协议以 `0` 表示未回报的窗口，而 0 小时不是任何额度会有的窗口，因此它到达区块时是缺失的，那一行便只写时刻。产品未给出方案的账号显示区块自身的未知标记，而不是任何人都没有授予的等级。

### 活动条与热力图序列

契约要求由供给方格式化五项活动数字，因为五者单位各异，只有供给方知道自己的数字带哪个单位。本包就是那个供给方，因此格式化在这里：

| 数字 | 回报字段 | 渲染为 |
|---|---|---|
| `total-tokens` | `totalTokens` | 千分位数字（`1,204,567`） |
| `peak-tokens` | `peakDayTokens` | 千分位数字 |
| `longest-task` | `longestTaskMinutes` | 整小时与分钟，带产品自己的后缀（`2h 5m`） |
| `current-streak` | `currentStreakDays` | 天数跨度，带产品自己的后缀（`3d`） |
| `longest-streak` | `longestStreakDays` | 天数跨度 |

产品未回报的数字完全不写进映射，因此活动条把该格画成未知；产品回报为零的数字则如实带上零，因为「回报了零」与「没有回报」是两个事实。按日序列以原始数字而非文本传递——热力图要把各天互相比较，需要的是数量本身——而没有用量的一天在其中保持缺失，不会以零到达。

三个单位后缀取自产品自己的 `SettingsPage.profileStats` 文案，四种随附语言皆然，因此 `2h 5m` 与 `3d` 在两侧界面读起来完全一致。

### 邀请状况

产品的推荐模型是「每个被邀请地址一行」。`inviteCredits` 成为已积攒的速率限制重置次数，`inviteCount` 成为已发送的邀请数量，而那些行本身——在 host 转发它们时——成为列表，每条各带该邀请自己的一次性链接、按重置时间同样方式格式化的创建时刻，以及以读者语言命名的状态。`pending`、`joined`、`rewarded` 是本版本有措辞的三种状态；其余状态一律丢弃而不打印，因为一个英文枚举成员在任何语言里都不是一句读得懂的话。三部分都没有回报时，整个邀请状况保持缺失——这既是没有推荐计划的部署的样子，也是推荐接口调用失败的样子。

按契约要求，限额名称与两条失败信息都是已本地化的文本，因此本包在四种随附语言（`en`、`zh-CN`、`zh-TW`、`ja`）中自行维护它们。它们是一张普通的表，而非 `ctx.locale` 命名空间：这些字符串是随账号一同传递的数据，不是某个渲染槽位的文案。切换语言只重新贴标签，不再读取 host：数字属于产品，不随读者语言改变。

`getSnapshot()` 是一次字段读取，在状态真正变化前始终返回同一个对象——重复且内容相同的读取既不发布也不通知，这正是区块按引用比较的渲染机制所要求的。头像也属于该状态的一部分，因此只更换了照片的保存同样会推动状态。

## 保存个人资料

`saveProfile({ displayName, avatar? })` 向 `/auth/profile` 提交一次变更，并回答 `saved`，或带 host 所给原因的 `failed`。四条性质是关键：

- **头像的三个字段要么一起传，要么都不传。** 缺失的 `image` 就是协议中「保留已存照片」的写法，因此只改名称的保存不携带任何图片字段，也就无法删除头像。确实携带图片的保存会同时带上它的 MIME 类型与扩展名：产品接受其中任一种识别方式，并在给出 MIME 类型时用它与 data URL 互相校验。
- **变更被存下后会重新读取一次 `/auth/account`。** 实际存下什么由产品决定——去掉首尾空白的名称、重新编码的照片——因此重新发布给区块的是已存的资料，而不是页面提交的内容。被拒绝时不发布任何内容：重绘同一份账号会读作一次成功的保存。
- **跨缝传递的是原因，不是措辞。** `failed` 仍不携带任何散文——失败提示是区块自身表单文案中的一行，那个包已在每种语言中拥有它。它携带的是 host 的 `reason`，即「**哪一种**拒绝」的稳定标识，与被拒绝的 provider 在本登录门中的传递方式完全一致。本版本读取的是 `name-required`、`avatar-format` 与 `avatar-payload` 三个；其余一律丢弃，表单回退到笼统的那一行，而不是把一个标识符打印给读者。
- **即便状态行不是 2xx，也读取正文。** 格式不合的补丁以 `400` 返回，原因写在正文里；把那份正文丢掉，正是被拒绝的保存过去到达表单时无话可说的原因。

此处不做任何校验。合法的显示名称与合法的头像由产品定义，在浏览器里再写一份规则只会做出不同的判断。

## 发送邀请

`sendInvite(email)` 向 `/auth/invite` 提交 `{ email }`，并回答 `sent`（host 回报链接时一并带上该邀请的链接）、`refused`、`unsupported` 或 `failed`。

拒绝以产品自己的标识到达，并在此处一次性翻译成区块的词汇：`invalid_email` → `invalid-email`、`self_invite` → `self-invite`、`already_invited` → `already-invited`。不在该表中的标识是本版本无法措辞的拒绝，按普通失败回报，而不是一次无名的拒绝。

`404` 与 `501` 读作 `unsupported` 而非失败：没有邀请路由的 host 是一个根本无法发送邀请的部署，卡片说明一次即可，而不是把它当成一次「重试也许能成」的失败发送。

已发出的邀请随后会重新读取 `/auth/account`，因为卡片显示的数量与余额属于产品。被拒绝时不重新发布任何内容，理由与被拒绝的保存相同：重绘同一份账号会读作一次成功的邀请。

## 组合顺序

两条依赖边，性质并不相同。

**向下，本包 inject `unieaiBootstrap`**——这是硬依赖，因为它是一条排序依赖，而 Cordis 中唯一能排定激活顺序的就是 `inject`。启动答复的供应方在其他插件函数体运行期间仍在读取，而 fiber 尚未 active 的服务是 `ctx.get` 读不到的；只是「找一找」的网关会找到空、自己去读 `/auth/account`，让取好的账号白白闲置。等待同时也保证本网关首次发布的状态就是已落定的那一份。因此两行一同出厂：保留本行却删掉启动行的组合，会让本 fiber 停在 pending——启动页会指名报出这一点。

**向上，`ui-unieai-account` 不依赖任何东西。** 区块在自身函数体运行期间以 `ctx.get` 读取本服务，并通过 `internal/service` 采纳后到的那一个，因此两者无论怎样排序它都能接上——如今它照例走的正是这条后到路径，因为本行要等启动答复，而区块什么都不等。这一切都发生在应用挂载之前，因此中间不会有任何东西被渲染出来。

## Model Experience

无，本包为设置界面读取一份账号描述；此处没有任何内容进入模型请求。

#### KV Cache effect

无；本包既不组装也不发送供应商请求。

## Known Limitations and Deferred Work

- **邀请明细取决于 host 是否转发** —— 产品为每个被邀请地址列出一行；登录门一直只把这份列表缩减为 `inviteCount`。本包在明细到达时读取它，未到达时只显示数量，因此 host 一旦转发，列表立刻出现，而在此之前此处不编造任何一行。
- **`/auth/invite` 是本包对 host 的诉求** —— 浏览器侧提交它、读取它的三个拒绝标识，并把 `404`/`501` 当作无法发送的部署。在登录门注册该路由之前，每次发送都回答 `unsupported`，卡片用一行说明。
- **Token 用千分位而非紧凑记法** —— 网页产品经 `Intl.NumberFormat` 的紧凑记法打印 `1.2M`；本包打印 `1,204,567`，与账号契约本身回避宿主 `Intl` 数据的做法一致：其输出在浏览器与 Node 测试运行之间并不相同。
- **zh-CN 的重置行是修正过的，并非逐字照抄** —— 产品自己的 `zh-cn` `meterReset` 字符串用的是繁体字；此处的简体词典把它写成简体，这是本包文案唯一偏离产品原文之处。
- **未命名账号以邮箱为标题** —— 契约中的 `displayName` 为必填，而产品对未设置名称的账号回报 `null`，因此由邮箱顶替。区块于是会显示两次邮箱，一次作为标题，一次作为邮箱。
- **重置时间未本地化** —— 采用 `YYYY-MM-DD HH:mm` 而非 `Intl`，与账号契约本身回避宿主 `Intl` 数据的做法一致：其输出在浏览器与 Node 测试运行之间并不相同。
- **不呈现 host 的失败文本** —— `/auth/account` 在失败时回答一条面向直接调用方的英文诊断信息。只有浏览器知道读者的语言，因此本包改用自己的本地化文案；它所区分的两种失败（产品不作答；本 host 不作答）就是区块能收到的全部细节。
- **每个文档只读一次，另加每次保存后一次** —— 没有轮询，也没有刷新手势。在另一个窗口消耗掉的额度、或改动过的个人资料，要到页面重新加载后才会反映出来。启动答复不改变这一点：它提供首个账号，以及某个部分迟到时的一次热追补；此后的一切都是本包自己的读取。
- **启动答复与新鲜读取无法区分** —— host 取好的 account 部分在本包采纳它时，最多可能已有一个缓存寿命那么旧（30 秒，实际上是登录到第一帧之间的那几秒）。此处不区分两者，因为在桌面端启动这一刻，取好的账号与刚读到的账号描述的是同一个产品状态。
- **只有三种拒绝有标识** —— 产品对被拒补丁回答的是英文散文（`Name is required`、`Unsupported avatar format`、`Invalid image payload`），把它们变成 `name-required`、`avatar-format`、`avatar-payload` 的是 host。措辞不同的拒绝到达表单时只是一次笼统失败。
- **头像随正文内联传输** —— 头像在账号快照与每次保存中都是 base64 `data:` URL，因此大图会在每次读取时重新传输。编辑器的 512px 裁切正是把它压到几百 KB 的原因；提高裁切尺寸的部署要在每次读取时为此付费。
