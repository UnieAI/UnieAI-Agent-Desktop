# @deepseek-ai/dsh-client-ui-settings-general

English | [中文](README.zh.md)

Settings shell, ownerless copy, and durable product-onboarding namespace. It occupies `sidebar.settings` with the trigger chrome and modal settings panel, fills `sidebar.nav.action` with the Plugins nav row that opens that panel, projects the `settings.section` ledger into the navigation and the `settings.onboarding` ledger into one mounted step at a time, and registers everything on the Settings pages that belongs to no single feature — the trigger/header/close chrome content, the local configuration-file action, the General section and its `settings.general.item` slot, and the `settings` dictionaries. The slot types it renders into belong to ui-settings, the settings domain base; only the shell's own contract types live here, because they reference ui-sidebar's slot type and the base layer must depend on no `ui-*` package. Feature-owned rows (Permission, Language, Appearance), sections (Models), and conditional onboarding steps stay with their feature packages.

The shell ships no onboarding copy of its own — all text arrives from registrants. Nav labels may be locale-following thunks, so the nav projection resolves them through `resolveSlotLabel` and re-renders on the section ledger bump or the locale revision (an optional `ctx.get('locale')` read; no hard locale dependency). The onboarding ledger projects in ascending order and mounts exactly one step at a time. Visible steps own their dialog chrome and app-root `inert` lifecycle; a mounted step still resolving private facts renders null, so nothing paints or blocks while it decides. The active registrant receives its id, `complete()`, and an `openSection(id)` callback; completing or skipping transfers ownership to the next entry. Registrants own durable completion, capability readiness, copy, mutations, and their visible wrapper, so independently registered flows cannot stack and the shell does not become a second configuration fact source.

A loopback browser loads the provider's `hasDocument` capability through `settings.describe` and renders **Open configuration file** only when the Host confirms that a provider-owned local document can be prepared. The action sends the pathless, loopback-only `settings.openDocument` request; the Host resolves the provider path again, materializes an absent document, and hands it to a native text editor (`open -t` on macOS, bypassing a browser file association; the desktop file association on Linux and Windows; Windows association after `wslpath -w` translation on WSL). Open failures keep the action available and render a localized error. Reopening the dialog or reconnecting refreshes availability after a transient read failure or Host topology change. Remote browsers never register the action and never issue the privileged settings read.

The Host half registers `ui-onboarding` in the user-settings seam. The welcome step contributed by `ui-settings-models` reads and writes its `welcomeNoticeVersion` through the existing public settings boundary; the shell itself remains policy-free.

## The sidebar seats

Expanded, the trigger is the reference column's own 15px chrome gear at the right end of the sidebar foot's identity row, in the tertiary ink — no row box, no label, because the row belongs to the sidebar seat and is shared with ui-unieai-account's account occupant. The label stays in the DOM as the button's accessible name and is taken out of the picture; a 15px glyph is too small to aim at, so the pointer target and the hover fill are a pseudo-element inset outside it and the glyph never moves. The 56px rail restores the same 36px circle every other rail control uses.

The Plugins nav row sits under New chat and opens this package's own panel at the `plugins` section. Panel open state, the requested section, and the anchor inside it live in an apply-level `SettingsPanelController` rather than in the shell's local state, because three surfaces open this panel: its own trigger, that nav row, and — through the `settingsPanel` service this package provides — the sidebar's account menu. A slot-declared store cannot serve the third: the render machinery creates those, so `apply` cannot write one, and `apply` is where a cordis service lives. The row hides itself while no `plugins` section is registered, so a composition without ui-settings-plugins draws no control with nothing behind it.

`settingsPanel` is `open(sectionId?, anchorId?)`. The anchor is forwarded verbatim to the named section through its `settings.section` owner share, and only to the section that was asked for — a fallback selection never inherits someone else's anchor. What an anchor means is the section's business; ui-unieai-account publishes three and scrolls to them.

The panel is the UnieAI Copilot settings dialog. It is 70vw wide by 90vh tall (capped at 900) at radius 8 from the 768px breakpoint up, 92vw from 640, and full screen with square corners below that; a header band spans its whole width carrying the heading, a one-line summary, and the registrant-owned actions, with the close button pinned to the panel's corner outside the band. Under the band one scroll region holds both columns centred together at a 1024px measure: a 176px navigation that sticks 16px below the top of the scroll, a 32px gap, and the section beside it. The band content is held to a 896px measure of its own. Below 768px the columns stack and the navigation becomes one horizontally scrolling strip of rows with its group headings hidden.

The panel navigation groups its rows the way the UnieAI web product's settings page does — small uppercase headings over runs of 36px rows at `8px 12px` and radius 6, the selected row taking the full-strength label at 500 over a fill and an unselected one the secondary ink at 400. That neutral fill is the reference's own decision and its reason carries: selection is a state rather than the screen's one wanted action, so it must not read as a coloured chip. Membership is a shell-owned map from section id to group, because the ledger carries no group and adding one to `settings.section` would make every registrant restate an arrangement of other registrants. A section the map does not name still lists, after the groups and under no heading. The group headings and the band's summary line are the copy this shell owns rather than receives; the summary describes the panel without enumerating sections, because which sections exist is a fact about the composition.

## Model Experience

None, as the plugin renders browser settings UI; nothing here reaches a model request.

#### KV Cache effect

None; this package neither assembles nor sends a provider request.

## Known Limitations and Deferred Work

- The General section has no built-in rows; each row appears only when its owning feature plugin is mounted.
- **The nav cell's radius is a literal 6px** — the reference settings page sets its nav chrome one step below `--dsw-radius-control`, and `--dsw-*` declares no token at that step. Reported to the theme owner rather than added here; ui-sidebar carries the same gap for its identity plate.
- **Nav group membership is a shell-owned id map** — a section this package does not name lists after the groups under no heading, so a new feature section joins a group only when this map is extended. Giving `settings.section` a group option instead would make each registrant restate an arrangement of its peers, which is why the map is here.
